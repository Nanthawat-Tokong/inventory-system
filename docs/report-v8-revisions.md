## A. บทคัดย่อ

### บทคัดย่อ (ภาษาไทย)

ธุรกิจที่มีหลายสาขามักบันทึกสต๊อกแยกกันและขอเบิกสินค้าผ่านโทรศัพท์หรือแอปพลิเคชันแชต ทำให้ไม่เห็นยอดคงเหลือของแต่ละสาขาแบบทันที และตรวจสอบย้อนหลังไม่ได้ว่าใครขอ อนุมัติ จัดส่ง หรือรับสินค้า โครงงานนี้พัฒนาระบบจัดการสินค้าคงคลังแบบเซ็นทรัลไลซ์ในรูปแบบเว็บแอปพลิเคชันด้วย React, Tailwind CSS, Node.js, Express และ MySQL/MariaDB ข้อมูลทุกสาขาเก็บในฐานข้อมูลเดียว การเคลื่อนไหวของสินค้าทุกครั้งบันทึกเป็นรายการรับเข้าหรือออกพร้อมผู้ทำรายการ และยอดคงเหลือคำนวณจากรายการเหล่านี้ สินค้าเข้าจากภายนอกได้ที่คลังหลักเท่านั้น ส่วนสาขารองได้รับสินค้าผ่านใบขอเบิก 6 สถานะ โดยผู้อนุมัติและพนักงานจัดส่งเป็นคนละบทบาท เมื่อสาขาได้รับของชำรุดหรือไม่ครบ ระบบเปิดเป็นเคสที่คลังหลักส่งของชดเชยได้หลายรอบ และปิดเคสได้เมื่อทั้งสองฝ่ายยืนยัน สิทธิ์ของผู้ใช้ 4 บทบาทควบคุมด้วย JSON Web Token ร่วมกับการตรวจบทบาทและขอบเขตสาขาจากฐานข้อมูลทุกคำขอ ระบบมีแดชบอร์ด การแจ้งเตือนสินค้าต่ำกว่าเกณฑ์รายสาขา และรายงาน 7 แบบที่ส่งออกเป็นไฟล์สำหรับ Excel ได้ ผลการทดสอบด้วย Jest ผ่าน 135 จาก 135 กรณี และการทดสอบผู้ใช้พร้อมกัน 10 คนเป็นเวลา 60 วินาที (27,866 คำขอ) มีเวลาตอบสนองที่เปอร์เซ็นไทล์ 95 เท่ากับ 45 มิลลิวินาที โดยไม่พบยอดสต๊อกติดลบหรือยอดคงเหลือที่ไม่ตรงกับผลรวมรายการรับเข้าและออก

> หมายเหตุ: ถ้าเก็บ UAT ได้ก่อนส่งเล่ม ให้เพิ่มประโยคท้าย เช่น "ผู้ใช้ทดลอง N คนให้คะแนนความพึงพอใจเฉลี่ย X.XX จาก 5"

### Abstract (English)

Multi-branch businesses often keep stock records separately and request goods by phone or chat, so no one sees branch stock in real time or can trace who requested, approved, shipped, or received a delivery. This project develops a web-based centralized inventory management system using React, Tailwind CSS, Node.js, Express, and MySQL/MariaDB. All branches share one database; every stock movement is recorded as a receive or issue transaction with the user who made it, and balances are computed from these records. New stock enters only at the main warehouse, while branches receive goods through a six-status requisition workflow in which the approver and the shipper are separate roles. When a branch receives damaged or missing items, the system opens a case that the warehouse can settle with one or more replacement shipments, and the case closes only when both sides confirm. Access for four user roles is controlled with JSON Web Tokens, with role and branch scope re-checked against the database on every request. The system also provides a dashboard, per-branch low-stock alerts, and seven reports that can be exported for Excel. All 135 Jest integration tests pass. In a 60-second load test with 10 concurrent users (27,866 requests), the 95th-percentile response time was 45 ms, with no negative stock and no balance that differed from the sum of its receive and issue records.

## B. 1.3 ขอบเขตของโครงงาน

ระบบมีบทบาทผู้ใช้ 4 ค่า (`admin`, `main_manager`, `staff`, `shipper`) สาขาคลังหลักกำหนดจากข้อมูลสาขา (`branches.is_warehouse = 1`) และมีได้สาขาเดียว บทบาท `main_manager` มีหน้าที่ต่างกันตามสาขาที่สังกัด: ถ้าสังกัดคลังหลักเป็นผู้อนุมัติ ถ้าสังกัดสาขารองเป็นผู้จัดการสาขานั้น ขอบเขตของแต่ละบทบาทเป็นดังนี้

### 1.3.1 ผู้ดูแลระบบ (Admin)
1. ดูแดชบอร์ด สต๊อก รายงาน และการแจ้งเตือนของทุกสาขา
2. จัดการข้อมูลสาขา (เพิ่ม แก้ไข ลบแบบซ่อน) และกำหนดสาขาคลังหลัก
3. จัดการบัญชีผู้ใช้ กำหนดบทบาท ผูกผู้ใช้กับสาขา และตั้งรหัสผ่านเริ่มต้นซึ่งผู้ใช้ต้องเปลี่ยนก่อนใช้งาน
4. จัดการข้อมูลสินค้า รับสินค้าเข้าคลังหลัก และบันทึกการออกสินค้า
5. อนุมัติ ปฏิเสธ หรือยกเลิกการอนุมัติใบขอเบิก ตอบเคสที่มีปัญหา ตัดสินใจเรื่องของชำรุด และขอปิดเคส แต่จัดส่งสินค้าและยืนยันรับสินค้าแทนสาขาไม่ได้
6. ตั้งเกณฑ์แจ้งเตือนสต๊อกต่ำรายสินค้าและรายสาขา และกำหนดสินค้าประจำสาขา

### 1.3.2 ผู้จัดการคลังหลัก (main_manager ที่สังกัดคลังหลัก)
1. ดูสต๊อกและรายงานของทุกสาขา
2. เพิ่ม แก้ไข และลบสินค้า รับสินค้าเข้าคลังหลัก และบันทึกการออกสินค้า
3. อนุมัติ ปฏิเสธ หรือยกเลิกการอนุมัติใบขอเบิก (การอนุมัติจองสินค้าไว้ให้ใบนั้น) แต่จัดส่งเองไม่ได้
4. จัดการเคสที่มีปัญหา: ตอบสาขา สร้างรายการจัดส่งชดเชย ตัดสินว่าของชำรุดให้ตัดทิ้งหรือส่งคืน และขอปิดเคส
5. กำหนดสินค้าประจำสาขาและตั้งเกณฑ์แจ้งเตือน

### 1.3.3 ผู้จัดการสาขารอง (main_manager ที่สังกัดสาขารอง)
1. ดูสต๊อกและรายงานของสาขาตนเอง
2. เพิ่มและแก้ไขข้อมูลสินค้า สร้างใบขอเบิก บันทึกการออกสินค้า และตรวจรับสินค้าของสาขาตนเอง
3. ตั้งเกณฑ์แจ้งเตือนของสาขาตนเอง

### 1.3.4 พนักงานสาขา (Staff)
1. ดูแดชบอร์ด สต๊อก การแจ้งเตือน และรายงานเฉพาะสาขาของตนเอง
2. สร้างใบขอเบิกจากสินค้าประจำสาขา โดยขอได้ไม่เกินจำนวนที่คลังหลักมีให้เบิก แก้ไขใบที่ถูกปฏิเสธแล้วส่งใหม่ หรือยกเลิกใบ
3. ตรวจรับสินค้า โดยแยกจำนวนสภาพดีและชำรุด ยืนยันรับของชดเชย และยืนยันหรือปฏิเสธคำขอปิดเคสจากคลังหลัก
4. บันทึกการออกสินค้า (ขาย ใช้ไป หรือเสียหาย) ของสาขาตนเอง โดยรับสินค้าเข้าสาขาโดยตรงไม่ได้

### 1.3.5 พนักงานจัดส่ง (Shipper, สังกัดคลังหลัก)
1. จัดส่งใบขอเบิกที่อนุมัติแล้ว ระบบตัดสต๊อกคลังหลักตามจำนวนที่มีจริง
2. จัดส่งรายการชดเชย
3. อนุมัติใบขอเบิก และบันทึกรับหรือออกสินค้าโดยตรงไม่ได้

### 1.3.6 ขอบเขตที่ไม่ครอบคลุม
1. ระบบบัญชีและการเงิน
2. การวางแผนเส้นทางและติดตามยานพาหนะขนส่ง
3. การเชื่อมต่อกับระบบชำระเงิน

## D. 3.1 กติกาของระบบ (แทน 6 ข้อเดิม)

1. รับสินค้าเข้าโดยตรงได้ที่สาขาคลังหลักเท่านั้น โดยผู้ดูแลระบบหรือผู้จัดการคลังหลัก กติกานี้ใช้กับทุกบทบาทรวมถึงผู้ดูแลระบบ
2. สาขารองได้รับสินค้าผ่านใบขอเบิกเท่านั้น และสาขาคลังหลักสร้างใบขอเบิกให้ตนเองไม่ได้
3. สาขาขอเบิกได้ไม่เกินจำนวน "เบิกได้" ของคลังหลัก คือยอดคงเหลือลบด้วยจำนวนที่อนุมัติให้ใบอื่นแล้วแต่ยังไม่จัดส่ง การอนุมัติจึงเป็นการจองสินค้า
4. ผู้อนุมัติกับผู้จัดส่งเป็นคนละบทบาท (Segregation of Duties) ผู้อนุมัติจัดส่งเองไม่ได้ และพนักงานจัดส่งอนุมัติเองไม่ได้
5. ยอดคงเหลือเปลี่ยนเมื่อจัดส่งหรือจัดส่งชดเชย (ออกจากคลังหลัก) และเมื่อสาขายืนยันรับของสภาพดี (เข้าสาขา) เท่านั้น ของชำรุดไม่เข้าสต๊อกสาขา
6. การยืนยันรับสินค้าทำได้เฉพาะผู้ใช้ที่สังกัดสาขาที่สร้างใบขอเบิก ผู้ดูแลระบบก็ยืนยันแทนไม่ได้
7. เคสที่มีปัญหาปิดได้สองทาง คือรับของชดเชยสะสมครบตามจำนวนที่อนุมัติ (ปิดอัตโนมัติ) หรือคลังหลักขอปิดและสาขายืนยัน ไม่มีฝ่ายใดปิดเคสได้ฝ่ายเดียว และของชำรุดทุกชิ้นต้องระบุว่าตัดทิ้งหรือส่งคืนก่อนปิดเคส
8. สาขารองเห็นและขอเบิกได้เฉพาะสินค้าที่ผู้จัดการคลังหลักหรือผู้ดูแลระบบเปิดให้สาขานั้น

## E. 3.2.1 Workflow Diagram (แทนย่อหน้าและตารางที่ 3)

Workflow Diagram ในภาพที่ 2 แสดงกระบวนการเบิกสินค้าจากคลังหลักไปยังสาขารอง แบ่งช่องตามผู้รับผิดชอบเป็น 3 ช่อง คือ สาขารอง ผู้อนุมัติคลังหลัก และพนักงานจัดส่ง กระบวนการเริ่มเมื่อพนักงานสาขาเห็นการแจ้งเตือนสินค้าใกล้หมดและสร้างใบขอเบิก โดยหน้าจอแสดงจำนวนที่คลังหลักมีให้เบิกเพื่อไม่ให้ขอเกิน ผู้อนุมัติตรวจแล้วอนุมัติ (จองสินค้า) หรือปฏิเสธพร้อมเหตุผล และยกเลิกการอนุมัติได้ก่อนจัดส่ง ซึ่งจะปล่อยสินค้าที่จองไว้ จากนั้นพนักงานจัดส่งกดจัดส่ง ระบบตัดสต๊อกคลังหลักตามจำนวนที่มีจริงและบันทึกรายการที่ส่งได้ไม่ครบ เมื่อสาขาตรวจรับ ระบบแยกจำนวนสภาพดีกับชำรุด ของสภาพดีเข้าสต๊อกสาขาทันที ถ้ามีของชำรุด ของขาดระหว่างทาง หรือคลังหลักส่งได้ไม่ครบ ใบจะเข้าสถานะพบปัญหาและแจ้งคลังหลักโดยอัตโนมัติ

ในสถานะพบปัญหา ทั้งสองฝ่ายส่งข้อความโต้ตอบกันในไทม์ไลน์ของใบได้ คลังหลักเลือกส่งของชดเชย (มีได้หลายรอบ) แจ้งว่าสต๊อกยังไม่พอ หรือขอปิดเคส ส่วนของชำรุดต้องตัดสินว่าให้สาขาตัดทิ้งหรือส่งคืนคลังหลัก ใบขอเบิกเสร็จสิ้นเมื่อสาขาได้รับของสภาพดีสะสมครบตามจำนวนที่อนุมัติ หรือเมื่อสาขายืนยันคำขอปิดเคส

## J. บทที่ 5 (แทนทั้งบท)

### 5.1 สรุปผลการดำเนินงาน

1. ข้อมูลสินค้า สาขา ผู้ใช้ และการเคลื่อนไหวของทุกสาขาเก็บในฐานข้อมูล `inventory_db` เพียงแห่งเดียว และสาขาคลังหลักกำหนดจากข้อมูลโดยไม่ต้องแก้โค้ด ตรงตามวัตถุประสงค์ข้อที่ 1
2. ระบบรองรับการจัดการสินค้าตาม SKU การรับเข้าที่คลังหลัก การออกสินค้า และการโอนย้ายผ่านใบขอเบิก 6 สถานะ ซึ่งจองสินค้าเมื่ออนุมัติ แยกผู้อนุมัติกับผู้จัดส่ง จัดส่งตามสต๊อกที่มีจริง และจัดการของชำรุดหรือขาดด้วยการส่งชดเชยหลายรอบและการปิดเคสที่ต้องตกลงสองฝ่าย ตรงตามวัตถุประสงค์ข้อที่ 2
3. การเคลื่อนไหวทุกครั้งบันทึกพร้อมผู้ทำรายการและยอดคงเหลือหลังทำรายการ ใบขอเบิกแยกจำนวนที่ขอ อนุมัติ จัดส่ง ได้รับสภาพดี และชำรุด และทุกการกระทำบันทึกในไทม์ไลน์ของใบ ผลทดสอบผู้ใช้พร้อมกัน 10 คนไม่พบยอดคงเหลือที่ไม่ตรงกับประวัติ ตรงตามวัตถุประสงค์ข้อที่ 3
4. ผู้ใช้ติดตามสต๊อกผ่านแดชบอร์ดที่รีเฟรชทุก 30 วินาที การแจ้งเตือนตามเกณฑ์รายสาขา และรายงาน 7 แบบ รวมถึงรายงานรายวัน รายสัปดาห์ และรายเดือน ที่ดาวน์โหลดเป็นไฟล์เปิดด้วย Excel ได้ ตรงตามวัตถุประสงค์ข้อที่ 4

### 5.2 ปัญหา อุปสรรค และข้อจำกัด

1. **การจัดส่งเมื่อสต๊อกไม่พอ** ในรุ่นแรก การจัดส่งล้มเหลวทั้งใบหากสินค้ารายการใดในคลังหลักไม่พอ ผู้จัดทำเพิ่มคอลัมน์ `shipped_qty` ให้จัดส่งตามสต๊อกที่มีจริง และต่อมาเพิ่มการจองสินค้าเมื่ออนุมัติ เพื่อไม่ให้ใบที่อนุมัติทีหลังแย่งสินค้าของใบที่อนุมัติก่อน
2. **การกำหนดขอบเขตสิทธิ์ที่กว้างเกินไป** แบบฟอร์มรับสินค้าในช่วงแรกให้ผู้ดูแลระบบเลือกรับเข้าสาขารองได้โดยข้ามใบขอเบิก และผู้อนุมัติเป็นคนจัดส่งเองได้ ผู้จัดทำจึงเพิ่มการตรวจฝั่ง Backend ว่าสาขาปลายทางต้องเป็นคลังหลัก และแยกบทบาทพนักงานจัดส่งออกจากผู้อนุมัติ
3. **การปิดเคสฝ่ายเดียว** เวอร์ชันก่อนให้คลังหลักปิดเคสที่พบปัญหาได้ทันที ซึ่งสาขาไม่มีโอกาสโต้แย้ง จึงเปลี่ยนเป็นคลังหลักขอปิดและสาขายืนยัน พร้อมเพิ่มไทม์ไลน์ข้อความโต้ตอบในใบ
4. **ข้อผิดพลาดเมื่อทำรายการพร้อมกัน** ชุดทดสอบ Jest พบว่า `stock_after` ซ้ำกันเมื่อรับเข้าหลายคำสั่งพร้อมกัน แม้จะล็อกแถวแล้ว สาเหตุคือระดับการแยกธุรกรรม `REPEATABLE READ` ทำให้ธุรกรรมที่รอล็อกยังอ่านค่าก่อนหน้า แก้โดยใช้ `READ COMMITTED`
5. **การเปลี่ยนโครงสร้างฐานข้อมูลระหว่างพัฒนา** โครงสร้างเปลี่ยน 12 ครั้งตลอดโครงงาน เช่น ปรับบทบาท เพิ่มการลบแบบซ่อน เพิ่มพนักงานจัดส่ง และเพิ่มตารางของชำรุด แต่ละครั้งต้องเขียน Migration ที่ย้ายข้อมูลเดิมได้ และต้องสำรองข้อมูลก่อนทุกครั้ง
6. **สภาพแวดล้อมการพัฒนา** Apache ใน XAMPP เปิดไม่ได้เพราะพอร์ต 80 ถูกโปรเซสของ Windows ใช้อยู่ จึงเปลี่ยนเป็นพอร์ต 8080 และข้อความภาษาไทยแสดงผิดเพี้ยนจนกำหนดชุดอักขระการเชื่อมต่อเป็น utf8mb4
7. **ข้อจำกัดของระบบ**
   - ยังไม่ได้นำขึ้นเซิร์ฟเวอร์จริง แม้เตรียมไฟล์ตั้งค่า Railway ไว้แล้ว
   - การทดสอบผู้ใช้พร้อมกันทำบนเครื่องเดียวกับฐานข้อมูลและมีสินค้า 5 รายการ จึงยังไม่ทราบพฤติกรรมเมื่อมีผู้ใช้หลายสิบคนผ่านเครือข่ายจริง
   - ยอดคงเหลือคำนวณจากผลรวมรายการทั้งหมด เมื่อข้อมูลสะสมหลายปีอาจช้าลง
   - ยังไม่มีบันทึกการใช้งาน (Audit Log) ของการแก้ไขข้อมูลหลัก เช่น การเปลี่ยนบทบาทผู้ใช้ แยกจากประวัติการเคลื่อนไหวสต๊อก
   - [ถ้ายังไม่ได้ทำ UAT] ยังไม่ได้ประเมินความพึงพอใจกับผู้ใช้จริงตามเกณฑ์ในโครงร่าง

### 5.3 ข้อเสนอแนะและงานในอนาคต

1. นำระบบขึ้นให้บริการบน Railway พร้อม HTTPS และทดสอบผู้ใช้พร้อมกันผ่านเครือข่ายจริง โดยเพิ่มจำนวนผู้ใช้จำลองเป็น 50–100 คน
2. ทดลองใช้งานกับธุรกิจหลายสาขาจริงเป็นระยะเวลาหนึ่ง แล้ววัดผลเทียบกับวิธีเดิม เช่น เวลาตั้งแต่ขอเบิกจนได้รับสินค้า และจำนวนครั้งที่ยอดในระบบไม่ตรงกับการนับจริง
3. เก็บยอดคงเหลือสรุปเป็นรายวัน (snapshot) แล้วคำนวณเฉพาะรายการหลังวันล่าสุด เพื่อให้ความเร็วไม่ลดลงเมื่อข้อมูลสะสมมากขึ้น
4. เพิ่ม Audit Log สำหรับการแก้ไขข้อมูลหลักและสิทธิ์ผู้ใช้
5. เพิ่มการแจ้งเตือนผ่าน LINE หรืออีเมลเมื่อมีใบที่รอผู้ใช้ดำเนินการ หรือสินค้าต่ำกว่าเกณฑ์
6. เพิ่มการสแกนบาร์โค้ดในขั้นตอนจัดส่งและตรวจรับ เพื่อลดการกรอกจำนวนด้วยมือ
